# Android build environment

## Use JDK 17 — not Android Studio's bundled `jbr`

```
JAVA_HOME = C:\Program Files\Java\jdk-17     ✅  17.0.6
JAVA_HOME = E:\Androidstudio\jbr             ❌  currently JDK 25.0.3
```

`run-release-build.bat` sets this for you and also re-applies the two fixes
below, so a fresh `expo prebuild` cannot silently reintroduce the failure.

## Why: the prefab / JNA stderr trap

**Symptom** — every one of these dies during configuration:

```
> Task :react-native-mmkv-storage:configureCMakeRelWithDebInfo[arm64-v8a] FAILED
> Task :react-native-worklets:configureCMakeRelWithDebInfo[arm64-v8a] FAILED
> Task :react-native-screens:configureCMakeRelWithDebInfo[arm64-v8a] FAILED
> Task :expo-updates:configureCMakeRelWithDebInfo[arm64-v8a] FAILED

* What went wrong:
Execution failed for task ':react-native-mmkv-storage:configureCMakeRelWithDebInfo[arm64-v8a]'.
> WARNING: A restricted method in java.lang.System has been called
```

There is no CMake error at all. The real output is in
`<module>/build/intermediates/cxx/RelWithDebInfo/<hash>/logs/<abi>/prefab_stderr.txt`:

```
WARNING: A restricted method in java.lang.System has been called
WARNING: java.lang.System::load has been called by com.sun.jna.Native in an
         unnamed module (file:.../com.google.prefab/cli/2.1.0/cli-2.1.0-all.jar)
WARNING: Use --enable-native-access=ALL-UNNAMED to avoid a warning for callers
         in this module
```

**Chain of events:**

1. AGP needs Prefab to resolve `react-android` / `fbjni` headers for CMake.
   `android.prefab.version=2.1.0` makes it run `com.google.prefab:cli` as a
   **child `java` process**.
2. That CLI uses JNA, which calls `System.load`. On **JDK 22+** `System.load`
   is a *restricted method*, so the JVM prints those warnings to **stderr**.
3. AGP's `GeneratePrefabPackages.reportErrors` (`GeneratePrefabPackages.kt:304`)
   reads the child's stderr line by line and throws
   `IllegalStateException` on it — so a mere warning becomes a fatal
   configure failure. (`prefab_stdout.txt` is 0 bytes; only stderr matters.)
4. JDK 17 and 21 have no such warning → the task passes.

## Two places pin the JVM — fix both

`JAVA_HOME` alone is **not** enough.

### 1. `android/gradle.properties`

```
org.gradle.jvmargs=-Xmx3072m -XX:MaxMetaspaceSize=768m --enable-native-access=ALL-UNNAMED
```

`--enable-native-access` is a **JDK 22+** option. With JDK 17 the JVM refuses
to start at all (`Unrecognized option`). It also does not help, because it only
affects the daemon — not the prefab child process.

Strip it: `org.gradle.jvmargs=-Xmx3072m -XX:MaxMetaspaceSize=768m`

### 2. `android/gradle/gradle-daemon-jvm.properties`

```
toolchainVersion=25     ❌ generated by `gradlew updateDaemonJvm`
toolchainVersion=17     ✅
```

This file is Gradle 9's **daemon JVM criteria**. Even with `JAVA_HOME` on 17,
`gradlew -version` reported:

```
Launcher JVM:  17.0.6
Daemon JVM:    Compatible with Java 25 ... (from gradle/gradle-daemon-jvm.properties)
```

The daemon — and therefore the prefab child it forks — still ran on 25.
Android Studio tends to recreate this file (via `updateDaemonJvm`) pointing at
its bundled `jbr`, which is how it drifts back.

## Verify

```
cd android
gradlew -version --no-daemon
```

Both `Launcher JVM` and `Daemon JVM` must be **17**. Then:

```
gradlew :react-native-mmkv-storage:configureCMakeRelWithDebInfo[arm64-v8a] --no-daemon
```

must say `BUILD SUCCESSFUL`.

## CI already does this correctly

`main.yml` and `release-all.yml` both use:

```yaml
uses: actions/setup-java@v5
with:
  distribution: 'zulu'
  java-version: '17'
```

CI also never writes `gradle-daemon-jvm.properties`, so the daemon there falls
back to the launcher JVM (17). Recent runs all report `success`. This is why
the failure only ever reproduced on the local machine.

## Unrelated but often confused with the above

Earlier local builds also died on:

```
NDK at C:\Users\WALTON\AppData\Local\Android\Sdk\ndk\27.1.12297006
  did not have a source.properties file
```

That was a corrupt NDK install (fixed by reinstalling through SDK Manager).
`CXX1101` is a *different* failure from the prefab trap above — check whether
`source.properties` exists before blaming the JDK.
